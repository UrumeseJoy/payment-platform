## 2. File-by-file summary

### Root
- **PaymentPlatformApplication.java** — Standard `@SpringBootApplication` entry point, calls `SpringApplication.run`.

### config/
- **KafkaConsumerConfig.java** — Defines a `DefaultErrorHandler` bean with exponential backoff (3 retries, 1000ms initial interval, 2.0 multiplier), and marks `IllegalStateTransitionException`/`IllegalArgumentException` as non-retryable.
- **KafkaTopicConfig.java** — Declares the `payment-events` Kafka topic (3 partitions, 1 replica) as a `NewTopic` bean.
- **RedisConfig.java** — Defines a `RedisTemplate<String, String>` bean with `StringRedisSerializer` for both keys and values.

### gateway/
- **GatewayOutcome.java** — Enum: `SUCCESS`, `DECLINED`, `TIMEOUT`.
- **GatewayResult.java** — Record wrapping `(GatewayOutcome outcome, String message)`.
- **MockPaymentGateway.java** — Deterministic fake gateway implementing `PaymentGateway`. Outcome is derived from the cents digits of the amount: cents ending in `13` → DECLINED, `99` → TIMEOUT, else SUCCESS. Same logic used for both `authorize()` and `capture()`.
- **PaymentGateway.java** — Interface with `authorize(UUID, BigDecimal)` and `capture(UUID, BigDecimal)`, both returning `GatewayResult`.

### ledger/entity/
- **EntryType.java** — Enum: `DEBIT`, `CREDIT`.
- **LedgerAccount.java** — Enum: `CUSTOMER_WALLET`, `MERCHANT_WALLET`, `PLATFORM_SUSPENSE`.
- **LedgerEntry.java** — Immutable JPA entity (no setters, no `@Version`, insert-only). Has a static `affectsLedger(PaymentStatus)` helper (true only for `CAPTURED`/`REVERSED`) and a static `pairFor(paymentId, event, amount)` factory that produces the two-row double-entry postings for `CAPTURED` (PLATFORM_SUSPENSE debit / MERCHANT_WALLET credit) and `REVERSED` (MERCHANT_WALLET debit / CUSTOMER_WALLET credit). Throws `IllegalArgumentException` for any other event.

### ledger/repository/
- **LedgerEntryRepository.java** — `JpaRepository<LedgerEntry, UUID>` with `findByPaymentId(UUID)`. Comment notes it's intended for a Tier-2 reconciliation job (not yet built).

### ledger/service/
- **LedgerService.java** — `applyTransition(paymentId, targetStatus)` retries up to 3 times on `OptimisticLockingFailureException` (throws `IllegalStateException` after exhausting retries). The actual transactional work (`applyOnce`, `@Transactional`) loads the payment, no-ops if already at target status, calls `payment.transitionTo(target)`, saves it, and if `LedgerEntry.affectsLedger(target)` is true, generates and saves the ledger entry pair.

### orchestration/messaging/
- **GatewayTimeoutException.java** — Simple `RuntimeException` subclass for gateway timeouts.
- **PaymentEvent.java** — Record `(UUID paymentId, PaymentEventType eventType, BigDecimal amount)`, the Kafka message payload (serialized to/from JSON via Jackson).
- **PaymentEventConsumer.java** — `@KafkaListener` on topic `payment-events`, group `payment-orchestration`. Deserializes the JSON message into `PaymentEvent`, then switches on `eventType`:
  - `PAYMENT_CREATED` → calls gateway `authorize()`; SUCCESS moves payment to `AUTHORIZED` (via `LedgerService`) and publishes `PAYMENT_AUTHORIZED`; DECLINED moves to `FAILED`; TIMEOUT throws `GatewayTimeoutException` (triggers Kafka retry).
  - `PAYMENT_AUTHORIZED` → calls gateway `capture()`; SUCCESS moves payment to `CAPTURED` (does NOT auto-publish further — comment explains SETTLED is a separate batch job not implemented in v1); DECLINED → `FAILED`; TIMEOUT → `GatewayTimeoutException`.
  - `PAYMENT_REVERSED` → directly calls `ledgerService.applyTransition(paymentId, REVERSED)`.
  - Any other event type → `IllegalArgumentException` ("Unsupported event type").
- **PaymentEventProducer.java** — Serializes a `PaymentEvent` to JSON and sends it via `KafkaTemplate<String,String>` to the `payment-events` topic, keyed by `paymentId`.
- **PaymentEventType.java** — Enum: `PAYMENT_CREATED`, `PAYMENT_AUTHORIZED`, `PAYMENT_CAPTURED`, `PAYMENT_REVERSED`. Note: `PAYMENT_CAPTURED` is defined but never produced or consumed anywhere in the codebase (capture success currently just updates the ledger directly with no follow-up event).

### payment/controller/
- **GlobalExceptionHandler.java** — `@RestControllerAdvice` mapping `PaymentNotReversibleException` → HTTP 409, and `IllegalArgumentException` → HTTP 404. Both return `{"error": "<message>"}`.
- **PaymentController.java** — `@RestController` at base path `/payments`. Two endpoints (see section 5).

### payment/dto/
- **CreatePaymentRequest.java** — Plain POJO (manual getters/setters, no Lombok) with `merchantId` (`@NotBlank`), `amount` (`@NotNull @Positive`), `currency` (`@NotBlank`).
- **PaymentResponse.java** — Plain POJO (manual getters/setters) with `id`, `merchantId`, `amount`, `currency`, `status` (String), `createdAt`.

### payment/entity/
- **IllegalStateTransitionException.java** — `RuntimeException` carrying `from`/`to` `PaymentStatus` fields, message "Cannot transition payment from X to Y".
- **Payment.java** — JPA entity, Lombok `@Getter` + package-private `@Setter`. Fields: `id`, `merchantId`, `amount` (NUMERIC(19,4) via precision/scale), `currency`, `status` (enum, string-mapped), `idempotencyKey` (unique), `version` (`@Version` — optimistic locking), `createdAt`/`updatedAt` (Hibernate timestamps). Constructor sets status to `CREATED`. `transitionTo(target)` validates against a static `LEGAL_TRANSITIONS` map:
  - `CREATED` → `{AUTHORIZED, FAILED}`
  - `AUTHORIZED` → `{CAPTURED, FAILED}`
  - `CAPTURED` → `{SETTLED, REVERSED}`
  - `SETTLED`, `FAILED`, `REVERSED` → `{}` (terminal)

  This matches the state machine locked in CLAUDE.md exactly. Throws `IllegalStateTransitionException` on illegal transitions. Note: the class Javadoc still contains a stale comment referencing a "TODO in orchestration package" for building the transition method — that transition method has since been implemented in this same class (see section 8, flagged as stale doc, not an actual TODO/stub).
- **PaymentNotReversibleException.java** — `RuntimeException`, thrown when reversal is attempted on a non-`CAPTURED` payment.
- **PaymentStatus.java** — Enum: `CREATED`, `AUTHORIZED`, `CAPTURED`, `SETTLED`, `FAILED`, `REVERSED`. Javadoc documents the state diagram.

### payment/repository/
- **PaymentRepository.java** — `JpaRepository<Payment, UUID>` with `findByIdempotencyKey(String)`.

### payment/service/
- **PaymentService.java** — Core service, two public methods:
  - `createPayment(request, idempotencyKey)`: checks Redis cache first (`idempotency:<key>`), then Postgres via `findByIdempotencyKey`, then attempts insert; on `DataIntegrityViolationException` (unique constraint race) reloads and returns the winning row instead of erroring. On successful new insert, publishes a `PAYMENT_CREATED` Kafka event and caches the response in Redis with a 24-hour TTL.
  - `reversePayment(paymentId)`: loads payment, throws `PaymentNotReversibleException` if not `CAPTURED`, otherwise publishes a `PAYMENT_REVERSED` event. **Does not itself change the payment's status** — the actual `REVERSED` transition + ledger posting happens asynchronously in `PaymentEventConsumer` when it consumes that event.

Only one migration file exists: **V1__init_schema.sql**

```sql
-- V1: core payment lifecycle tables (Tier 1 scope)
-- No outbox_events table yet — v1 publishes to Kafka post-commit in
-- application code. Known gap: possible crash between commit and publish.
-- Documented trade-off, not an oversight — see README design decisions.

CREATE TABLE payments (
    id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    merchant_id      VARCHAR(255) NOT NULL,
    amount           NUMERIC(19, 4) NOT NULL CHECK (amount > 0),
    currency         VARCHAR(3) NOT NULL,
    status           VARCHAR(20) NOT NULL,
    idempotency_key  VARCHAR(255) NOT NULL,
    version          INTEGER NOT NULL DEFAULT 0,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT uq_payments_idempotency_key UNIQUE (idempotency_key)
);

CREATE INDEX idx_payments_status ON payments (status);
CREATE INDEX idx_payments_merchant_id ON payments (merchant_id);

CREATE TABLE ledger_entries (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    payment_id      UUID NOT NULL REFERENCES payments (id),
    account         VARCHAR(30) NOT NULL,
    entry_type      VARCHAR(10) NOT NULL CHECK (entry_type IN ('DEBIT', 'CREDIT')),
    amount          NUMERIC(19, 4) NOT NULL CHECK (amount > 0),
    related_event   VARCHAR(20) NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()

    -- Deliberately no updated_at: rows in this table are never updated,
    -- only inserted. That immutability is the whole point of the ledger.
);

CREATE INDEX idx_ledger_entries_payment_id ON ledger_entries (payment_id);
```

No `outbox_events` table exists (explicitly documented as a known Tier-1 gap/trade-off in the migration header). No V2+ migrations exist.

## 6. Kafka topics, event types, listeners

**Topic:** `payment-events` — declared via `KafkaTopicConfig` (`NewTopic` bean), 3 partitions, 1 replica. Only one topic exists in the whole codebase.

**Event types** (`PaymentEventType` enum):
- `PAYMENT_CREATED` — produced by `PaymentService.createPayment()`
- `PAYMENT_AUTHORIZED` — produced by `PaymentEventConsumer.handlePaymentCreated()` on successful gateway authorization
- `PAYMENT_CAPTURED` — **defined in the enum but never produced or consumed anywhere** (dead/unused enum value)
- `PAYMENT_REVERSED` — produced by `PaymentService.reversePayment()`

**Producer:** `PaymentEventProducer.publish(PaymentEvent)` — serializes to JSON, sends to `payment-events` keyed by `paymentId`.

**Listener:** `PaymentEventConsumer.onMessage(String message)` — single `@KafkaListener(topics = "payment-events", groupId = "payment-orchestration")`. Deserializes JSON to `PaymentEvent`, then dispatches by `eventType`:
- `PAYMENT_CREATED` → `handlePaymentCreated` (calls gateway.authorize, transitions to AUTHORIZED or FAILED, publishes PAYMENT_AUTHORIZED on success)
- `PAYMENT_AUTHORIZED` → `handlePaymentAuthorized` (calls gateway.capture, transitions to CAPTURED or FAILED; does not publish a further event)
- `PAYMENT_REVERSED` → directly transitions payment to REVERSED via `LedgerService`
- any other type → throws `IllegalArgumentException`

**Retry/error handling:** `KafkaConsumerConfig` registers a `DefaultErrorHandler` with exponential backoff (3 retries max, 1s initial interval, 2x multiplier), excluding `IllegalStateTransitionException` and `IllegalArgumentException` from retry (fails fast on those). `GatewayTimeoutException` is retryable (not excluded), simulating retry-on-gateway-timeout.

No Dead Letter Queue / DLQ topic is configured (Tier 2, not built). No Transactional Outbox pattern is implemented — explicitly documented as a known gap in `V1__init_schema.sql`.

## 7. Test classes

Three test classes exist total:

1. **`LedgerEntryTest`** (`ledger/entity/LedgerEntryTest.java`) — pure unit test, no Spring context.
   - `capturedPairBalances()`: verifies `LedgerEntry.pairFor(..., CAPTURED, ...)` produces a debit/credit pair whose sums are equal (double-entry balance check).
   - `authorizedEventThrows()`: verifies `pairFor` throws `IllegalArgumentException` for an event with no defined ledger postings (`AUTHORIZED`).

2. **`PaymentTest`** (`payment/entity/PaymentTest.java`) — pure unit test, no Spring context.
   - `capturedToSettled_isLegal()`: walks a payment through `CREATED → AUTHORIZED → CAPTURED → SETTLED` and asserts final status.
   - `createdToSettled_throwsException()`: asserts a direct `CREATED → SETTLED` transition throws `IllegalStateTransitionException`.

3. **`PaymentServiceIdempotencyTest`** (`payment/service/PaymentServiceIdempotencyTest.java`) — `@SpringBootTest` + Testcontainers Postgres (real DB), Redis is `@MockBean`-mocked (not a real Testcontainer — comment explains the idempotency guarantee under test lives in the DB unique constraint, not the cache).
   - `sequentialDuplicateRequestReturnsOriginalPayment()`: two sequential calls to `createPayment` with the same idempotency key return the same payment ID; only one row persisted.
   - `concurrentDuplicateRequestsCreateExactlyOnePayment()`: 10 threads racing to create a payment with the same idempotency key; asserts exactly 1 row persisted and all 10 responses resolve to the same payment ID (tests the `DataIntegrityViolationException` race-handling path in `PaymentService.createPayment`).

No tests exist for: `PaymentEventConsumer`/Kafka orchestration flow, `LedgerService.applyTransition` (optimistic-lock retry logic), `PaymentController` (no `@WebMvcTest` / MockMvc tests), `MockPaymentGateway`, `GlobalExceptionHandler`, payment reversal flow end-to-end.
